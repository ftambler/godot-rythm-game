7. Development order

Don't build everything at once. I'd do it in this order:

1. Player
   ↓
2. 8-direction movement
   ↓
3. Wall + bouncing
   ↓
4. Shield system
   ↓
5. Spike walls + damage
   ↓
6. Toggle orb
   ↓
7. Speed trigger
   ↓
8. Level JSON loader
   ↓
9. Music / timing
   ↓
10. Level Select
   ↓
11. Settings

For your first playable prototype, you only need:

Game.tscn
│
├── Player.tscn
├── Wall.tscn
└── UI

Get ball → movement → shield → wall → bounce working first. Everything else can be layered on top of that architecture.

would you say the scope of this project is enough for a one semester course in game developing for uni?

Yes. More than enough, especially if this is your first game-development project.

The key is to treat the project as a small but complete rhythm game, rather than trying to make a huge number of levels or mechanics.

What makes it a good university project

You have several areas you can demonstrate technically:

   └── Game state
		 │
		 ▼

   ├── Object spawning
   ├── Timed events
   └── Level progression
		 │
		 ▼
Game Architecture
   │
   ├── Reusable scenes
   ├── Components
   ├── Resource management
   └── UI / menus
		 │
		 ▼
Audio / Rhythm
   │
   ├── BPM
   ├── Timing
   └── Synchronization

The rhythm/timing system is probably the part I'd give the most attention to. It takes the project from "ball game with obstacles" to an actual rhythm game.

What I would NOT add

For a one-semester project, avoid:

✗ Multiplayer
✗ Online leaderboards
✗ Procedural levels
✗ Level editor
✗ Complex story
✗ Inventory
✗ Character customization
✗ Dozens of levels
✗ Multiple game modes

If you finish early, those become optional extensions.

A very reasonable semester progression
Weeks 1–2
Godot + basic player
        ↓
Weeks 3–4
Movement + bouncing + shields
        ↓
Weeks 5–6
Obstacles + damage + speed
        ↓
Weeks 7–8
Music synchronization + timing
        ↓
Weeks 9–10
JSON level system
        ↓
Weeks 11–12
Menus + level selection + settings
        ↓
Weeks 13–14
Content + polish + testing

I'd actually consider the JSON-driven level system + rhythm synchronization to be your strongest academic component. It gives you something more interesting to explain than simply "I made several levels by placing objects in the editor."

So yes: the scope is appropriate, provided you keep the content small and focus on making the underlying systems solid.
